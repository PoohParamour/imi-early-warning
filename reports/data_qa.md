## หมวด 1: ที่มาของข้อมูล

**What: ใช้ข้อมูลอะไรบ้าง?**
3 กลุ่ม: (1) ข้อมูลหลัก IMI ของ สนค. (2) ข้อมูลภายนอก คือค่าเงินและราคาน้ำมันจาก FRED (3) ข้อมูลเสริม ได้แก่ CPI/PPI ของ สนค. สำหรับวัดราคาในประเทศ ปฏิทินวันเผยแพร่ IMI และราคาปุ๋ยกับนมโลกสำหรับรอบที่ 2

**Because: ข้อมูลเป็น Open Data จริงไหม มีหลักฐานอะไร?**
- IMI อยู่บน data.go.th (ชุดข้อมูล `tpso_data_70`) ใบอนุญาต Open Data Common
- CPI อยู่บน GD Catalog ใบอนุญาต Open Data Common
- FRED เป็น Public Domain (ขออ้างอิง) และ World Bank Pink Sheet เป็น CC BY 4.0
- ทุกแหล่งดาวน์โหลดได้ฟรี ไม่ต้องใช้ API key และบันทึก URL จริงไว้ใน `sources.json`

**Why: ทำไมใช้ข้อมูลจาก FRED ไม่ใช้ของ ธปท.?**
API ของ ธปท. ต้องลงทะเบียนและรออนุมัติ เราใช้ข้อมูล Federal Reserve ซึ่งอ้างอิงได้ และ feature เป็น % การเปลี่ยนแปลง ความต่างจากอัตราอ้างอิงในไทยจึงน่าจะน้อย (ยังไม่ได้วัด เขียนเป็นข้อจำกัด)

**What: ดึงข้อมูลอย่างไร?**
- IMI: ส่งคำขอ POST ทีละเดือน 320 ครั้ง (1 คำขอ = 1 เดือน ใส่ 81 รหัส) ไม่มีคำขอล้มเหลว
- FRED: ดาวน์โหลดไฟล์ CSV ด้วย `curl` เพราะ Python `requests` เกิด timeout ซ้ำ ขณะที่ `curl` ดาวน์โหลด URL เดียวกันสำเร็จ
- ทุกไฟล์ตั้งชื่อด้วย timestamp UTC กันเขียนทับ

**Why: ทำไมต้องเก็บ request manifest ด้วย?**
เพื่อตรวจย้อนกลับได้ว่าส่งคำขออะไรไปบ้าง (เดือน รหัส จำนวนแถวที่ได้) ไฟล์ `imi_request_manifest` มี 320 รายการ ตรงกับ 320 เดือน

**What: `sources.json` มีอะไร ทำไมสำคัญ?**
ทะเบียนของทุกไฟล์: ชื่อแหล่ง เจ้าของ URL วิธีเรียก เวลาดาวน์โหลด จำนวนแถว ช่วงข้อมูล ชื่อไฟล์ SHA-256 ใบอนุญาต ข้อความอ้างอิง สำคัญเพราะใช้พิสูจน์ได้ว่าข้อมูลมาจากไหนและไม่ถูกแก้

**Because: SHA-256 ใช้ทำอะไร?**
เป็น "ลายนิ้วมือ" ของไฟล์ ถ้าแก้ไฟล์แม้ 1 ตัวอักษร ค่าจะเปลี่ยน ทุก notebook เทียบ SHA-256 ก่อนใช้ไฟล์ ถ้าไม่ตรงจะหยุดทันที

**What: ข้อมูลอ้างอิงอย่างไร?**
มีข้อความอ้างอิงในแต่ละรายการของ `sources.json` และรวมในรายงานหัวข้อเอกสารอ้างอิง

## หมวด 2: ไฟล์แต่ละไฟล์ใน `data/raw/`

**What: `imi_monthly_...csv` คืออะไร?**
ดัชนีราคานำเข้ารายเดือน 81 รหัสสินค้า × 320 เดือน = 25,752 แถว ไม่มีค่าว่างและไม่มีแถวซ้ำ ทุกรหัสที่ใช้มีครบ 320 เดือน

**What: คอลัมน์สำคัญของไฟล์ IMI มีอะไร?**
- `commodityCode`, `commodityNameTH` รหัสและชื่อกลุ่ม
- `year` (พ.ศ.), `month`
- `index` ค่าดัชนี (ตัวที่เราใช้)
- `change` % เทียบเดือนก่อน, `changeYear` % เทียบปีก่อน
- `yearBase` ปีฐาน = 2555
- `createdAt` วันที่ API สร้างข้อมูล

**Because: ทำไม `createdAt` สำคัญ?**
ทุกแถวมีค่าเดียวกัน (2026-09-28) แปลว่า API สร้างข้อมูลใหม่ทั้งชุด เราจึงตรวจประวัติการแก้ไขข้อมูลย้อนหลังไม่ได้ ถ้าเคยแก้ จะเกิด leakage เล็กน้อยที่เรามองไม่เห็น เขียนไว้เป็นข้อจำกัด

**What: รหัสที่ใช้ในงานคืออะไร?**
`318` ปุ๋ยและยากำจัดศัตรูพืช · `402` นมและผลิตภัณฑ์นม · `100` เชื้อเพลิง (ตรวจ pipeline) · `000` รวมทุกรายการ ที่เหลืออีก 77 รหัสเก็บเป็นข้อมูลดิบแต่ไม่ได้ใช้

**What: `imi_master_...json` คืออะไร?**
รายชื่อรหัสและช่วงข้อมูลที่ API แจ้ง (IMI 81 รหัส, EXI 83 รหัส) ใช้กำหนดว่าต้องดึงเดือนไหนบ้าง จึงไม่ต้องใส่ตัวเลขช่วงเวลาเองในโค้ด

**What: ปฏิทินเผยแพร่ IMI คืออะไร ทำไมต้องมี?**
ไฟล์ 21 แถวที่ไล่เก็บจากข่าวของ สนค. ว่าแต่ละเดือนข้อมูลออกวันไหน (พ.ย. 2024 – ก.ค. 2026) ช้ากว่าสิ้นเดือน 26–41 วัน ใช้กำหนดวันพยากรณ์เป็นวันที่ 15 ของเดือน t+2 เพราะทุกเดือนออกไม่เกินวันที่ 10 ของ t+2

**Why: ทำไมต้องไล่ดูข่าวเอง ไม่ใช้วันที่จากข้อมูล?**
เพราะข้อมูลที่ API ให้มีแต่วันที่สร้างข้อมูลใหม่ (`createdAt`) ซึ่งไม่ใช่วันที่เผยแพร่ครั้งแรก

**What: ข้อมูลค่าเงินกับน้ำมันเป็นอย่างไร?**
รายวัน ค่าเงินเริ่มปี 1981 น้ำมันเริ่มปี 1987 มีค่าว่างในวันหยุดตลาด (ค่าเงิน 536 วัน น้ำมัน 1,173 วัน) เราใช้เฉพาะตั้งแต่ปี 2000

**Why: ทำไมดึงข้อมูลย้อนไปถึงปี 1981 ทั้งที่ใช้ตั้งแต่ปี 2000?**
เพราะดาวน์โหลดทั้งไฟล์ได้ในคำขอเดียวและเก็บเป็นข้อมูลดิบครบ ส่วนการเลือกช่วงทำในขั้นเตรียมข้อมูล

**What: ไฟล์ CPI และ PPI คืออะไร ใช้ทำอะไร?**
- CPI: ดัชนีราคาผู้บริโภคหมวดนมและผลิตภัณฑ์นม (รหัส 11320, 297 เดือน)
- PPI: ดัชนีราคาผู้ผลิต 2 รหัส (3105 ผลิตภัณฑ์นม, 3201 เคมีภัณฑ์ขั้นมูลฐาน ปุ๋ยเคมี พลาสติก) 140 เดือนต่อรหัส
- ใช้วัดว่าราคาในประเทศตามหลังราคานำเข้ากี่เดือน ไม่ใช้เป็น feature หรือ target

**Because: ทำไม CPI ดึง 320 คำขอแต่ได้ 297 แถว?**
เพราะ API มีข้อมูลหมวดนี้ตั้งแต่ ธ.ค. 2001 คำขอ 23 ครั้งแรกจึงได้ผลว่าง ไฟล์เก็บเฉพาะที่มีข้อมูล

**What: ไฟล์ Pink Sheet และ FAO คืออะไร?**
สำหรับรอบที่ 2: Pink Sheet (Excel) มีราคายูเรียและ DAP รายเดือน ดอลลาร์ต่อตัน ส่วน FAO (CSV) มีดัชนีราคานมโลก (Dairy, 2014–2016 = 100) ทั้งสองมีข้อมูลถึง ก.ย. 2026

**Because: เปิดไฟล์ Pink Sheet และ FAO ต้องระวังอะไร?**
- Pink Sheet มีหัวตารางหลายบรรทัด ข้อมูลเริ่มบรรทัดที่ 7 เดือนเขียนเป็น `2026M09` และชื่อคอลัมน์ `Urea` มีช่องว่างท้ายชื่อ
- FAO มีบรรทัดอธิบาย 3 บรรทัดก่อนหัวตาราง

**What: ข้อมูลภายนอกอื่นที่ใช้มีใบอนุญาตอะไร?**
FRED: Public Domain (ขออ้างอิง) · World Bank: CC BY 4.0 · FAO: ตาม FAO Terms [ยังไม่ยืนยันรายละเอียด] · ปฏิทินเผยแพร่และ PPI: [ยังไม่ยืนยันหน้าชุดข้อมูล]

## หมวด 3: คุณภาพข้อมูล

**What: ตรวจคุณภาพข้อมูลอย่างไร?**
ตรวจ schema (คอลัมน์ครบ) · ค่าซ้ำ (ไม่มี) · ค่าว่าง (IMI ไม่มี) · ความต่อเนื่องของทุกเดือนต่อรหัส · ค่าดัชนีต้องเป็นบวก (เพราะใช้ log) · และ SHA-256 ของทุกไฟล์

**Because: ข้อมูลครบทุกเดือนจริงไหม?**
กลุ่ม 100, 318, 402 และ 000 มีครบ 320 เดือนทุกกลุ่ม (assert ใน notebook 01) ส่วนรหัสอื่น 3 รหัส (315, 401, 417) หยุดเผยแพร่กลางทาง แต่ไม่ใช่กลุ่มที่ใช้

**What: ข้อมูลรายวันมีปัญหาอะไร?**
- มีค่าว่างในวันหยุด
- ในแต่ละเดือน ค่าเงินมีข้อมูลทั้งเดือนต่ำสุด 18 วัน น้ำมันต่ำสุด 9 วัน (มัธยฐานทั้งสองอยู่ที่ 21 วัน)

**Why: ทำไมไม่เติมค่าศูนย์ในวันหยุด?**
เพราะศูนย์จะดึงค่าเฉลี่ยต่ำผิดความจริง ราคาน้ำมัน 0 ดอลลาร์ไม่มีอยู่จริง เราเฉลี่ยเฉพาะวันที่มีข้อมูล

**What: น้ำมันมีเดือนที่ข้อมูลน้อยผิดปกติไหม?**
มี 3 เดือน: ธ.ค. 2000, พ.ย. 2002, มี.ค. 2006 (มีข้อมูลทั้งเดือน 10, 10 และ 9 วัน) วันที่ขาดเป็นวันทำการ และส่วนใหญ่ค่าเงินในวันเดียวกันมีค่า จึงเป็นช่องว่างของข้อมูลต้นทาง สาเหตุเชิงลึกยังไม่ยืนยัน

**Because: เดือนเหล่านั้นกระทบผลไหม?**
ไม่ เพราะกระทบเฉพาะแถวที่เดือนฐาน t ไม่เกิน ก.ย. 2006 ซึ่งอยู่ในช่วงฝึก ไม่กระทบ validation และ test

**Why: ทำไมไม่เติมค่าหรือตัดเดือนเหล่านั้นทิ้ง?**
เพราะเฉลี่ยจากวันที่มีก็ยังใช้ได้ และไม่กระทบช่วงที่ใช้วัดผล การเติมค่าจะเป็นการสร้างข้อมูลที่ไม่มีจริง

**What: ข้อมูลมี outlier ไหม จัดการอย่างไร?**
มีการเปลี่ยนแปลงแรง เช่น ปุ๋ยพุ่งราว 32% ต้นปี 2026 เป็นเหตุการณ์จริงของตลาด ไม่ใช่ข้อผิดพลาดของข้อมูล เราไม่ตัดทิ้ง เพราะจะทำให้ผลดูดีเกินจริง

**What: ข้อมูลมีความเอนเอียง (bias) หรือข้อมูลส่วนบุคคลไหม?**
- ไม่มีข้อมูลส่วนบุคคล เป็นดัชนีรวมระดับกลุ่มสินค้าและราคาตลาดรายวัน
- ความเอนเอียงที่ต้องรู้: IMI สะท้อนราคาเฉลี่ยของทั้งกลุ่ม ไม่ใช่ราคาของผู้ซื้อแต่ละราย และสรุปแทนสินค้ากลุ่มอื่นไม่ได้

## หมวด 5: การกันข้อมูลรั่ว (leakage) ที่เกี่ยวกับข้อมูล

**What: feature แต่ละตัวใช้ข้อมูลถึงวันไหน?**
- feature ประวัติ IMI และ feature ถึงเดือน t: ใช้ข้อมูลถึงเดือน t
- feature ของเดือน t+1 (ค่าเงินและน้ำมัน): ใช้ข้อมูลทั้งเดือน t+1 ซึ่งจบก่อนวันพยากรณ์ (วันที่ 15 ของ t+2)

**Because: ตรวจอย่างไรว่าข้อมูลของเดือน t+1 ไม่เกินวันพยากรณ์?**
เก็บวันที่ observation ล่าสุดที่ใช้ไว้ในคอลัมน์ `*_max_date` แล้วตรวจทุกแถวว่าอยู่ก่อน `forecast_origin` ผ่าน 0 violation จาก 8 เงื่อนไข

**Why: ทำไมการตรวจนี้ยังไม่พิสูจน์ว่าข้อมูลเผยแพร่ทันจริง?**
เพราะเดือน t+1 จบก่อนวันที่ 15 ของ t+2 อยู่แล้วโดยสูตร การตรวจนี้ยืนยันว่าสูตรถูก แต่ FRED ไม่เก็บ vintage ว่าแต่ละวันเผยแพร่เมื่อไร เราจึงใช้ release cadence ของผู้เผยแพร่เป็นตัวแทน (H.10 เผยแพร่รายสัปดาห์) และเขียนเป็นข้อจำกัด

**What: `target_available_date` คืออะไร ใช้ทำอะไร?**
วันที่คำตอบของแถวนั้นเผยแพร่ = วันที่ 15 ของเดือน (เดือนเป้าหมาย + 2) ใช้คัดแถวฝึก: ณ วันพยากรณ์ใด ใช้ได้เฉพาะแถวที่ `target_available_date` ไม่เกินวันนั้น

**What: ผู้ตรวจอิสระตรวจข้อมูลอย่างไร?**
คำนวณ target และ feature ซ้ำจากข้อมูลดิบ (IMI, FRED) ทุกแถวที่สุ่ม ได้ผลต่างไม่เกิน 10⁻¹³ และตรวจ `*_max_date` ว่า feature แบบเต็มเดือนใช้ข้อมูลอยู่ในเดือน t+1 และแบบ cutoff24 ไม่มีวันเกินวันที่ 24

**Because: ข้อมูลรอบที่ 2 (ราคาปุ๋ยและนมโลก) ใช้อย่างไรให้ไม่รั่ว?**
สมมติว่าค่ารายเดือนของเดือน t+1 เผยแพร่ไม่เกินวันที่ 10 ของ t+2 (ปฏิทิน FAO ปี 2026 เผยแพร่วันที่ 2–9 และไฟล์ Pink Sheet ปรับปรุงวันที่ 2 ต.ค.) แต่วันเผยแพร่ย้อนหลังและการปรับแก้ค่าย้อนหลังยังไม่ยืนยัน

### ก. การดึงข้อมูล (ขั้น 1–6)

**ถาม: ทำไมอ่าน MasterData ก่อน ไม่กำหนดช่วงเดือนในโค้ดเอง?**
- **ทำอะไร:** อ่านรายชื่อรหัสและเดือนเริ่ม/สิ้นสุดจาก API แล้วสร้างรายการเดือนจากค่านั้น (ปีฐาน เดือนเริ่ม เดือนสุดท้าย)
- **ทางเลือก:** ใส่ ม.ค. 2000 ถึง ส.ค. 2026 ตายตัวในโค้ด
- **ทำไมเลือกแบบนี้:** ถ้า สนค. เพิ่มเดือนใหม่หรือเปลี่ยนปีฐาน โค้ดจะปรับตามเอง ไม่ต้องแก้ และกันการขอเดือนที่ API ไม่มีข้อมูล
- **ข้อจำกัด:** ถ้า API เปลี่ยนรูปแบบ MasterData โค้ดจะหยุดที่ assert ซึ่งเป็นผลที่ต้องการ

**ถาม: ทำไมส่งคำขอทีละเดือน (320 ครั้ง) ไม่ดึงทั้งหมดครั้งเดียว?**
- **ทำอะไร:** 1 คำขอ = 1 เดือน ใส่รหัสทั้ง 81 ตัวในคำขอเดียว
- **ทางเลือก:** ขอครั้งเดียวทั้งช่วง
- **ทำไมเลือกแบบนี้:** API ออกแบบให้รับ 1 เดือนต่อคำขอ ไม่มีโหมดดึงช่วง การส่งรหัสทั้ง 81 ตัวพร้อมกันลดจำนวนคำขอจาก 25,920 เหลือ 320

**ถาม: ทำไมหน่วงเวลา 0.3 วินาทีระหว่างคำขอ?**
- **ทำไม:** ไม่ให้ยิง API ของหน่วยงานรัฐถี่เกินไปจนถูกจำกัดอัตรา (HTTP 429) หรือสร้างภาระเกินจำเป็น
- **ผล:** 320 คำขอใช้เวลาไม่นาน และไม่มีคำขอล้มเหลว

**ถาม: ถ้าคำขอล้มเหลวกลางทางจะเกิดอะไร?**
- **ทำอะไร:** มี retry สูงสุด 5 ครั้ง ถอยรอเพิ่มทีละขั้น (backoff 1 วินาที) กับรหัสตอบกลับ 429, 500, 502, 503, 504 และมี timeout 60 วินาที
- **ทำไมเลือกแบบนี้:** ข้อผิดพลาดชั่วคราวของเซิร์ฟเวอร์ควรลองใหม่ แต่ข้อผิดพลาดอื่น (เช่น 404) ควรหยุดทันที
- **ผลจริง:** ไม่มีคำขอล้มเหลวเลย (`failed_request_count = 0`)

**ถาม: ตรวจอย่างไรว่าข้อมูลที่ได้ถูกเดือนและครบ?**
ตรวจ 5 ข้อทุกครั้ง:
1. ผลตอบกลับต้องเป็นรายการที่ไม่ว่าง (ถ้าว่างจะ error ระบุเดือนที่ขาด)
2. ปีและเดือนในผลตอบกลับต้องตรงกับที่ขอ
3. ไม่มีแถวซ้ำของ (รหัส, ปี, เดือน)
4. เดือนที่ได้กลับมาต้องตรงกับชุดเดือนที่ควรได้ทั้งหมด
5. กลุ่ม 000, 100, 318, 402 มีครบ 320 เดือนและไม่มีค่าว่าง

**ถาม: ทำไมใช้ `curl` ดึง FRED ไม่ใช้ Python `requests`?**
- **เหตุการณ์จริง:** Python `requests` เกิด read timeout ซ้ำกับ FRED ขณะที่ `curl` ดาวน์โหลด URL เดียวกันสำเร็จ
- **ทำอะไร:** เปลี่ยนเป็น `curl` พร้อม timeout (เชื่อมต่อ 15 วินาที รวม 60 วินาที) และ retry 3 ครั้ง
- **ทำไมเลือกแบบนี้:** แก้ที่ตัวส่งข้อมูล ไม่ได้เปลี่ยนข้อมูล เก็บข้อความ byte ต้นฉบับโดยตรง
- **ข้อจำกัด:** ไม่ทราบสาเหตุที่ `requests` timeout (ไม่ได้ตรวจเชิงลึก)

**ถาม: ตรวจอะไรกับไฟล์ FRED หลังดาวน์โหลด?**
คอลัมน์ต้องเป็น `observation_date` กับชื่อ series วันที่เรียงจากเก่าไปใหม่ เริ่มไม่เกิน ม.ค. 2000 และสิ้นสุดไม่ก่อนเดือนล่าสุดของ IMI ถ้าข้อใดไม่ผ่านจะหยุด

**ถาม: ไล่ดึงวันเผยแพร่ IMI จากข่าวอย่างไร?**
- **ทำอะไร:** เปิดทุกหน้าของ archive ข่าวประชาสัมพันธ์ของ สนค. ดึงข้อมูล JSON ที่ฝังในหน้าเว็บ คัดข่าวที่ชื่อมีคำว่าดัชนีราคาส่งออก-นำเข้า ดึง **เดือนอ้างอิง** จากชื่อข่าวด้วย regex (ชื่อเดือนไทย + ปี พ.ศ.) และเอา **เวลาเผยแพร่** จากฟิลด์ของข่าว
- **คำนวณ:** lag = วันที่เผยแพร่ − วันสิ้นเดือนอ้างอิง
- **ถ้ามีข่าวซ้ำเดือนเดียวกัน:** เก็บฉบับล่าสุด (`drop_duplicates(..., keep='last')`)
- **ทำไมเลือกแบบนี้:** ไม่มีตารางวันเผยแพร่ทางการให้ดาวน์โหลด ข่าวคือหลักฐานวันเผยแพร่ที่ตรวจสอบได้
- **ข้อจำกัด:** ได้แค่ 21 เดือนล่าสุด เพราะ archive ที่ค้นได้มีเท่านี้ และการแปลงชื่อข่าวด้วย regex อาจพลาดถ้ารูปแบบชื่อเปลี่ยน (ตรวจแล้วได้ 21 เดือนไม่มีซ้ำ)

**ถาม: ทำไมต้องตรวจ SHA-256 ก่อนอ่านทุกไฟล์?**
- **ทำไม:** ถ้าไฟล์เปลี่ยน แม้แต่ตัวอักษรเดียว ผลที่สร้างจะต่าง notebook จึงหยุดทันทีเมื่อค่าไม่ตรงกับ `sources.json`
- **ทางเลือก:** ไม่ตรวจ แล้วเชื่อว่าไฟล์ไม่ถูกแก้
- **ข้อจำกัด:** ป้องกันการแก้ไฟล์ แต่พิสูจน์ไม่ได้ว่าต้นทางไม่ได้ปรับแก้ข้อมูลก่อนเราโหลด

**ถาม: ทำไมค่าเริ่มต้นของ notebook 01 คืออ่านจาก snapshot ไม่ดึงใหม่?**
- **ทำไม:** กด Run All แล้วต้องได้ข้อมูลชุดเดิม ไม่ให้ผลเปลี่ยนเพราะ API มีเดือนใหม่ และไม่ยิง API ซ้ำ
- **ทำอะไร:** flag `DOWNLOAD_*` เป็น False ถ้าไม่พบ snapshot จะหยุดพร้อมข้อความ ไม่ดาวน์โหลดเอง

### ข. การเตรียมข้อมูล (ขั้น 7–8)

**ถาม: ทำไมแปลงข้อมูลรายวันเป็นรายเดือนด้วยค่าเฉลี่ย?**
- **ทำอะไร:** เฉลี่ยค่ารายวันที่ไม่ว่างในเดือนนั้น (`groupby` เดือน → mean) หลังกรองให้เริ่มตั้งแต่ 1 ม.ค. 2000 และตัดวันที่เป็นค่าว่าง
- **ทางเลือก:** ใช้ค่าวันสุดท้ายของเดือน หรือค่ามัธยฐาน
- **ทำไมเลือกค่าเฉลี่ย:** ค่าเฉลี่ยทั้งเดือนลดผลของความผันผวนวันเดียว และสอดคล้องกับธรรมชาติของ IMI ที่เป็นราคารายเดือน และใน Scope (ตรวจก่อนเริ่มโครงการ) บันทึกว่าค่าเฉลี่ยรายเดือนที่คำนวณจาก DEXTHUS ต่างจากชุดรายเดือน EXTHUS ของ Federal Reserve ไม่เกิน 0.06 บาท [ผลตรวจนั้นไม่ได้อยู่ใน notebook ปัจจุบัน]
- **ข้อจำกัด:** ไม่ได้ทดสอบว่าค่าวันสุดท้ายของเดือนให้ผลต่างหรือไม่

**ถาม: ทำไมคำนวณค่าเฉลี่ยสองแบบ (ทั้งเดือน และวันที่ 1–24)?**
- **ที่มา:** แผนเดิมวางวันพยากรณ์ไว้วันที่ 25 จึงต้องใช้ข้อมูลถึงวันที่ 24
- **ปัจจุบัน:** ใช้แบบทั้งเดือนเป็นหลัก (วันพยากรณ์วันที่ 15 ของ t+2 ข้อมูลเดือน t+1 ครบแล้ว) และเก็บแบบวันที่ 1–24 เป็นชุด 3-cutoff24 เพื่อทดสอบความไว
- **ผล:** MAE ต่างกันน้อยมาก (ปุ๋ย 6.367 เทียบ 6.402) ข้อสรุปไม่ขึ้นกับวิธีนี้

**ถาม: ทำไมเก็บ `full_max_date` และ `cutoff24_max_date` ด้วย?**
เพื่อใช้ตรวจ leakage: วันที่ observation ล่าสุดที่ใช้สร้าง feature ต้องอยู่ก่อนวันพยากรณ์ ถ้าไม่เก็บ จะตรวจย้อนหลังไม่ได้

**ถาม: ทำไม feature ใช้ log change ไม่ใช้ % ธรรมดา?**
- **ทำไม:** log change บวกกันข้ามช่วงเวลาได้ (เปลี่ยน 1 เดือน 3 ครั้งรวมเป็น 3 เดือน) สมมาตรเมื่อขึ้นและลง และใกล้ % เมื่อเปลี่ยนไม่มาก
- **ข้อจำกัด:** ต้องการดัชนีเป็นบวก (ตรวจแล้วทุกค่าเป็นบวก)

**ถาม: ทำไมใช้หน้าต่าง 1, 2, 3, 6, 12 เดือน?**
- **ที่มา:** กำหนดตั้งแต่ต้นใน Scope ให้ครอบคลุมระยะสั้นถึงรายปี
- **ข้อจำกัด:** ไม่ได้ทดลองหน้าต่างอื่น ผลที่ตามมาคือต้องมีข้อมูลย้อนหลัง 12 เดือน จึงเริ่มตารางที่ ม.ค. 2001

**ถาม: ความผันผวน 6 เดือน คำนวณอย่างไร?**
- **ทำอะไร:** ส่วนเบี่ยงเบนมาตรฐานของการเปลี่ยนแปลงรายเดือน (log × 100) ในหน้าต่างเลื่อน 6 เดือน (`rolling(6, min_periods=6).std(ddof=1)`)
- **`min_periods=6`:** ไม่คำนวณถ้ามีข้อมูลไม่ครบ 6 เดือน เพื่อไม่ให้ค่าจากหน้าต่างที่ไม่เต็มปนเข้ามา
- **`ddof=1`:** ใช้ค่าเบี่ยงเบนแบบตัวอย่าง (หาร n−1) ซึ่งเป็นมาตรฐานเมื่อมีข้อมูลเป็นตัวอย่าง

**ถาม: feature ของเดือน t+1 (`lead_t1`) คำนวณอย่างไร?**
- **ทำอะไร:** 100 × [log(ค่าเฉลี่ยรายเดือนของ t+1) − log(ค่าเฉลี่ยของ t)] โดยเลื่อนค่าเฉลี่ยขึ้นหนึ่งเดือน (`shift(-1)`)
- **ทำไมเทียบกับเดือน t:** เพราะเรารู้ข้อมูลเดือน t เต็ม และต้องการสัญญาณว่าเดือนที่ IMI ยังไม่ออกเคลื่อนไปทางไหน
- **ต่างจาก target อย่างไร:** `shift(-1)` ของค่าเงินและน้ำมันเป็นข้อมูลที่ ณ วันพยากรณ์ออกครบแล้ว ส่วน `shift(-h)` ของ IMI คือคำตอบที่ยังไม่รู้ ต้องแยกให้ชัดเพราะเป็นจุดที่ leakage เกิดง่าย

**ถาม: ทำไมสร้างคำตอบด้วย `shift(-h)` แยกตามกลุ่ม?**
- **ทำอะไร:** เลื่อน IMI ในแต่ละกลุ่มสินค้าแยกกัน (`groupby('commodity_code').shift(-h)`)
- **ทำไม:** ถ้าเลื่อนรวมทั้งตาราง แถวสุดท้ายของกลุ่มหนึ่งจะดึงค่าจากแถวแรกของอีกกลุ่ม
- **เงื่อนไขที่ต้องจริง:** `shift` ได้ผลถูกต้องเมื่อข้อมูลของแต่ละกลุ่มเรียงตามเดือนและไม่มีเดือนขาด ซึ่งตรวจแล้ว (ครบ 320 เดือนทั้ง 3 กลุ่ม)

**ถาม: ทำไมแถวสุดท้ายของแต่ละ h ถึงหายไป?**
เพราะแถวที่เดือนเป้าหมายอยู่หลัง ส.ค. 2026 ยังไม่มีคำตอบ จึงตัดออกจากตารางสร้างโมเดล (`dropna`) ตัวอย่าง h=3 เดือนฐานสุดท้ายคือ พ.ค. 2026 แถวเหล่านี้ย้ายไปอยู่ใน `latest_features.csv` เพื่อใช้พยากรณ์จริง

**ถาม: ตารางเก็บแบบ long (แยก horizon เป็นแถว) ทำไมไม่เก็บเป็นคอลัมน์ y_h2…y_h6?**
- **ทำไมเลือก long:** แต่ละ h มีเดือนที่ใช้ได้ต่างกัน และมีวันที่คำตอบพร้อมใช้ต่างกัน (`target_available_date`) การเก็บเป็นแถวทำให้คัดแถวฝึกตามวันที่ได้ตรง ๆ
- **ข้อจำกัด:** ข้อมูลฝั่ง feature ซ้ำในทุก horizon ทำให้ไฟล์ใหญ่ขึ้น (ประมาณ 2.4 MB)

**ถาม: ทำไมใช้ `merge(..., validate='many_to_one')`?**
เพื่อตรวจว่าตาราง feature ภายนอกมี 1 แถวต่อ 1 เดือน ถ้าผิดปกติ (เช่น เดือนซ้ำ) โค้ดจะ error ไม่ปล่อยให้ข้อมูลถูกคูณซ้ำเงียบ ๆ

**ถาม: จัดการค่าที่หายไป (missing) อย่างไร?**
- **IMI:** ไม่มีค่าว่าง
- **ข้อมูลรายวัน:** ตัดวันที่ว่างก่อนเฉลี่ย ไม่เติมค่า
- **feature ที่คำนวณไม่ได้:** (เช่น 12 เดือนแรก) ตัดแถวทิ้ง ไม่เติมค่า
- **ทำไมไม่ impute:** การเติมค่าอาจใช้ข้อมูลอนาคตโดยไม่ตั้งใจ (เช่น interpolate) และ missing ในงานนี้เกิดจากโครงสร้าง ไม่ได้สุ่ม
- **ตรวจผล:** ตารางสุดท้ายมี 0 เซลล์ว่างในคอลัมน์ feature และคำตอบ

**ถาม: จัดการ outlier อย่างไร?**
ไม่ตัดและไม่ปรับ เพราะค่าสูงสุด เช่น ปุ๋ยพุ่ง 32% เป็นเหตุการณ์จริงของตลาด การตัดออกจะทำให้ผลดูดีเกินจริง และไม่ตรงกับสิ่งที่ผู้ใช้เจอจริง

**ถาม: เดือนที่ดัชนีไม่ขยับ (ปุ๋ย 12%) กระทบการทำนายไหม?**
ที่ระดับรายเดือนทำให้ No-change ได้เปรียบ (ทายถูกเป๊ะในเดือนที่ไม่ขยับ) แต่ target ของเราเป็นการเปลี่ยนสะสม h เดือน จึงมีโอกาสเป็นศูนย์พอดีน้อยลงมาก (ในช่วง test ที่ h=3 สัดส่วนแถวที่ y = 0 พอดีของปุ๋ยเป็น 0% และของนมราว 1%) เราไม่ปรับอะไร ถือเป็นลักษณะของข้อมูล

**ถาม: ทำไมเลือกเฉพาะ 3 กลุ่มจาก 81 รหัส?**
- **เกณฑ์:** ข้อมูลต่อเนื่องครบ · ดัชนีขยับบ่อยพอ (ตัดกลุ่มที่ไม่ขยับเกินครึ่ง) · กลไกราคาต่างกัน · ผู้ใช้ชัด · ไม่ถูกตัวแปรอื่นครอบงำ
- **ข้อควรเปิดเผย:** เคยทดลองเบื้องต้นกับ 10 กลุ่มซึ่งมีปุ๋ยแต่ไม่มีนม ผลชุดนั้นมี leakage และยกเลิกแล้ว

### ค. การตรวจคุณภาพและ leakage (ขั้น 9)

**ถาม: การตรวจ leakage 8 ข้อคืออะไรบ้าง?**
1. สูตรวันพยากรณ์ถูกต้อง (วันที่ 15 ของเดือน t+2)
2. สูตรเดือนเป้าหมายถูกต้อง (t + h)
3. คำตอบของแถวที่ทำนายต้อง **ยังไม่เผยแพร่** ณ วันพยากรณ์ (`target_available_date` หลัง `forecast_origin`)
4–5. ข้อมูลค่าเงินและน้ำมันแบบเต็มเดือน: วัน observation ล่าสุดต้องอยู่ก่อนวันพยากรณ์
6–7. เช่นเดียวกันสำหรับแบบวันที่ 1–24
8. feature ที่ต้องใช้ต้องไม่ว่าง
ผลคือ 0 violation ทุกข้อ

**ถาม: ทำไมการตรวจข้อ 4–7 ผ่านเสมอ แล้วยังมีประโยชน์ไหม?**
- **ตรงไปตรงมา:** ผ่านเสมอตามสูตร เพราะเดือน t+1 จบก่อนวันที่ 15 ของ t+2 อยู่แล้ว
- **ประโยชน์:** ยืนยันว่าโค้ดไม่ได้ใช้ข้อมูลเกินเดือน t+1 โดยบังเอิญ (เช่น จาก bug) แต่ **ไม่พิสูจน์** ว่าข้อมูลเผยแพร่ทันจริง ซึ่งเป็นจุดที่ต้องพึ่งหลักฐานวันเผยแพร่
- **ที่ควรพูดถ้าถูกถาม:** ยอมรับตรง ๆ ว่าเป็นการตรวจความสอดคล้องของสูตร ไม่ใช่ข้อพิสูจน์

**ถาม: ทำไมตรวจ leakage ทั้งตอนสร้างตารางและตอนฝึกโมเดล?**
เพราะ leakage เกิดได้หลายชั้น: ตอนสร้าง feature (ตารางนี้) · ตอนเลือกแถวฝึก (`training_rows` ใน notebook 04) · ตอนปรับมาตรฐาน feature · ตอนเลือกโมเดลจาก validation (จุดที่ผู้ตรวจอิสระพบ 45 จุด) ตารางที่ผ่านการตรวจชั้นเดียวไม่พอ

**ถาม: ผู้ตรวจอิสระตรวจข้อมูลอย่างไร?**
- คำนวณ target และ seasonal naive ซ้ำจากข้อมูลดิบทุกแถว ผลต่างต่ำกว่า 9.7×10⁻¹⁴
- ทวน feature `lead_t1` ทุกแถวจาก FRED ผลต่างต่ำกว่า 9.1×10⁻¹⁴ (ก่อนหน้านี้ทีมก็สุ่มตรวจ target 300 แถวเองได้ผลต่างไม่เกิน 3.6×10⁻¹⁵)
- ตรวจว่าทุก origin เลือกแถวฝึกถูก 2,040 origin
- รัน notebook 01 → 06 ใน kernel ใหม่ ตัวเลขใน `logs/metrics/` 28 จาก 31 ไฟล์ตรงทุก byte อีก 3 ไฟล์ต่างเฉพาะส่วนที่แก้

**ถาม: ตารางสุดท้ายรู้ได้อย่างไรว่าไม่มี bug เรื่องวันที่?**
มี 3 หลักฐาน: (1) assert จำนวนแถวต่อ h และต่อกลุ่ม (2) leakage audit 8 ข้อ (3) ผู้ตรวจอิสระคำนวณซ้ำจากข้อมูลดิบ แต่ทั้งหมดยืนยันความสอดคล้องกับ **กติกาที่เราตั้ง** ถ้ากติกาเอง (วันที่ 15) ผิดในช่วงก่อนปี 2024 จะตรวจไม่พบ

### ง. ข้อมูลที่ใช้วัด pass-through (CPI/PPI)

**ถาม: ทำไมใช้ปีฐานล่าสุดของ CPI และ PPI?**
- **ทำอะไร:** เลือกปีฐานที่ใหม่ที่สุดจาก MasterData (CPI ปีฐาน 2566, PPI ปีฐาน 2564) และขอข้อมูลตามปีฐานนั้น
- **ทำไม:** ปีฐานล่าสุดมีข้อมูลต่อเนื่องถึง ส.ค. 2026 ขณะที่ปีฐานเก่ากว่าหยุดก่อนหน้านั้น (เช่น PPI ปีฐาน 2558 สิ้นสุด ธ.ค. 2568)
- **ข้อจำกัด:** PPI ในชุดนี้เริ่ม ม.ค. 2015 จึงมีก่อนช่วง test เพียง 47 เดือน

**ถาม: ทำไมเทียบในรูปบาท (IMI × ค่าเงิน) ไม่เทียบในรูปดอลลาร์?**
เพราะราคาในประเทศ (CPI, PPI) เป็นบาท การเทียบที่หน่วยเดียวกันจึงถูกต้อง ราคานำเข้าในรูปบาทรวมผลของค่าเงินด้วย ซึ่งเป็นสิ่งที่ผู้ซื้อในไทยเจอ

**ถาม: ใช้ข้อมูลช่วงไหนวัด pass-through ทำไม?**
เฉพาะก่อน ม.ค. 2019 (ช่วงฝึกและ validation) เพื่อไม่ให้ช่วง test มีผลต่อเรื่องที่เล่า ซึ่งสอดคล้องกับหลักไม่ใช้ test ปรับสิ่งใด

**ถาม: ทำไมมี dummy ของเดือนในสมการ?**
เพื่อควบคุมฤดูกาลของราคาในประเทศ (ราคาบางเดือนเปลี่ยนตามเทศกาลไม่เกี่ยวกับราคานำเข้า) ถ้าไม่ควบคุม ความสัมพันธ์ที่วัดอาจปนกับรูปแบบรายเดือน

**ถาม: ทำไมใช้ HAC standard error?**
เพราะการเปลี่ยนแปลงรายเดือนของราคามีความสัมพันธ์ต่อเนื่องข้ามเดือน ค่าความคลาดเคลื่อนมาตรฐานแบบธรรมดาจะแคบเกินจริง HAC (Newey–West) ปรับให้ถูกต้อง
